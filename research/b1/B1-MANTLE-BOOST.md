# B1：攀爬加速（Mantle Boost）和准心计时圆环

日期 2026-10-24。R5Flowstate（S21 客户端 + S3 专用服务器）。数据在 [data/](data/)，脚本 [analyze_b1.py](analyze_b1.py)、[aggregate_b1.py](aggregate_b1.py)。

标记：
- **[bin]**：读 `r5apex_dx12.exe` 得到；
- **[sdk]**：读社区 SDK 源码得到（只写重新表述的规则，不贴源码）；
- **[meas]**：本次实测。

## 0. 结论

1. **它不是 S21 原生的东西。** Mantle boost 是官方在 **S27** 上线的玩法；我们在 S21 上看到它，是因为 Flowstate 社区把它移植到了 SDK 里。
   - `r5apex_dx12.exe` 里没有任何 mantle boost / sweet spot 字符串：Ghidra `StringUse` 和全文件扫描都是 0 [bin]。
   - exe 里只有原生的攀越字段（`m_traversalProgress`、`m_traversalRefPos`、`m_traversalForwardDir` 等），SDK 用的就是这些 [bin]。
2. **判定靠的是"角度差"，不是固定时间。**
   - 角度差 = 攀爬动画镜头的俯仰 − 玩家准心的俯仰。
   - 在原版里，这个差**只是动画加在镜头上的一条俯仰曲线**，和玩家往哪看无关：准心俯仰 −30°、0°、+30° 的曲线一样 [meas]。
3. **曲线不是一条，而是按攀爬类型分开。** 但每一类内部非常稳定。
   - 站姿、h120 以上：36 次，开窗时刻的进度 0.768 ± 0.015。
   - 开窗都在攀爬末尾：站姿各类是最后约 **0.12–0.19 s**；蹲姿更宽，见 §4。
4. **开启 boost 后，超级滑铲被 boost 取代。**
   - 在窗口内按"跳 + 蹲"，结果是 BOOST（388.7 / 367.42），不是原生的 460 [meas]。
5. **Unity 可以复刻。** 每一类一条俯仰曲线，加 SDK 的三条判定，就能得到同样的窗口和圆环。见 §7。

## 2. 判定规则 [sdk]

按下激活键（默认是跳）时，前提是：
- 攀越类型是 mantle；
- 不在悬挂中；
- 本次攀爬还没判定过。

满足前提后，按顺序检查：

| # | 条件 | 不满足 → |
|---|---|---|
| 1 | 能取到动画镜头（第一人称代理正在播放攀越动画） | FAILED（nocam） |
| 2 | 角度差 δ ≥ 0，并且不大于上一帧的 δ（正半边、正在回落）（`mantle_boost_require_decreasing_view_angle` 1） | FAILED（dec） |
| 3 | \|δ\| < 1.5°（`bridge_mantle_boost_sweet_spot_angle`） | FAILED（angle） |
| 4 | 动画进度 > 0.5（`mantle_boost_min_valid_traversal_frac`） | FAILED（frac） |
| — | 都满足 | **BOOST** |

δ 的取法：
1. 把第一人称代理的动画定在当前进度；
2. 用玩家视角调原生 `GetTraversalViewPosition`，得到动画镜头角度；
3. δ = 动画俯仰 − 玩家俯仰。

一次攀爬只判定一次；判定之后再按无效。

**攀爬结束时**（SDK 在原生速度之后覆盖）：

| 结果 | 水平 | 竖直 |
|---|---|---|
| BOOST | 冲刺姿态速度 × 1.3 = 299 × 1.3 = **388.7**，沿输入方向 | √(2·750·90) = **367.42** |
| FAILED | 299 | √(2·750·56) = **289.83**（普通跳） |
| 没按 | 299（冲刺）/ 199.5（走） | 0 |

BOOST 之后到落地前，lurch / tap-strafe 被关掉（`mantle_boost_disables_tap_strafes`）。

## 3. 圆环怎么画 [sdk]

- **圆环大小**：把 1.5° 换算成屏幕上的距离：0.5 · sin(1.5°) / (cos(1.5°) · tan(半竖直视场))。
- **中心点位置**：准心相对"当前渲染视角（动画镜头）"的屏幕偏移，算法相同。所以中心点到圆环中心的距离就是 δ。
- **sweet spot 进度**：每种攀越状态第一次出现时，从进度 0.5 往后每 0.01 扫一次，记下第一个 \|δ\| < 1.5° 的进度，之后一直用这个值。它决定圆环在哪一刻"合上"。
- 标签 "BOOST"；松开后圆环还留 0.25 s（`mantle_boost_rui_persist_time`）。

从两个偏移可以反推每帧的角度差：δ = atan(cho / vao · tan 1.5°)。其中 cho 是准心偏移，vao 是 1.5° 换算的偏移。本次实测就是这样得到逐帧曲线的。

## 4. 实测

### 4.1 方法

- Gibraltar，120 fps，岩石 lane A，`--geometry h<H>`；开启 `mantle_boost_enabled=1`。
- **新的客户端逐帧记录器**（`hsd_trial.py --mb-log`，日志前缀 `[B1-MB]`）：每帧记下状态、动画进度、sweet spot、vao、cho、视角和速度。
- 同时打开 SDK 自带的两个日志：
  - `bridge_mantle_boost_trig_log`：每次按键的 δ、进度和哪一条检查拦下；
  - `bridge_mantle_boost_rui_log`：每种攀越状态的 sweet spot。
- 计划表 `b1_<接近方式>_<按键>_k<K>_p<俯仰>`：
  - 接近方式：`spr` 冲刺跳；`walk` 走路跳；`ang` 斜 30° 冲刺；`wd` 视线偏 45°、按 W+D；`cr` 冲刺跳后按住蹲。
  - 按键：`none` 只看；`mb` 只按跳；`sg` 跳 + 蹲，也就是超级滑铲的按法。
  - K：攀越开始后第几帧按。
  - 俯仰：`p0`、`pm30`（往上看 30°）、`pp30`（往下看 30°）。
- 会话：
  - `B1_h120`：33 次，覆盖所有接近方式、俯仰，以及 K 的扫描；
  - `B1_h80`、`B1_h100`、`B1_h160`、`B1_h200`：每个 6 次；
  - `B1_h120cr`：蹲姿和斜向按键，9 次。
  - **有效攀爬共 61 次（不含每个会话的热身）。**
- h60 被直接跳过去，不会触发攀爬；h300 冲刺跳够不到，也不会触发。这两个高度没有数据。
- 6 次试验的帧率被标记（96–116 fps，要求 120 ± 3 %）。逐帧曲线按时间算，所以仍然保留。

开窗 = 按 §2 规则，第一个满足的帧；窗口一直开到攀爬结束。

| 类别 | n | 时长 T（s） | 峰值 δ（°） | 峰值所在进度 | 开窗进度 | 开窗时剩余（s） |
|---|---|---|---|---|---|---|
| 站姿 h80 | 4 | 0.313 | 6.23 | 0.14 | 0.62 ± 0.06 | 0.138（0.117–0.158） |
| 站姿 h100 | 4 | 0.467 | 5.54 | 0.29 | 0.70 ± 0.03 | 0.156（0.142–0.183） |
| **站姿 h120–h200** | **36** | 0.571 | 4.85 | 0.43 | **0.768 ± 0.015** | **0.144（0.125–0.158）** |
| 站姿 h120，视线偏 45° | 5 | 0.561 | 3.20 | 0.42 | 0.70 ± 0.01 | 0.186（0.175–0.192） |
| 蹲姿 h80 | 2 | 0.517 | 5.41 | 0.30 | 0.82 | 0.208 |
| 蹲姿 h100 | 2 | 0.625 | 4.52 | 0.42 | 0.72 | 0.271 |
| 蹲姿 h120（短） | 2 | 0.650 | 3.98 | 0.51 | 0.77 | 0.163 |
| **蹲姿 h120（长）** | 6 | 0.813 | 2.48 | 0.23 | **0.51**（由"进度 > 0.5"决定） | **0.468** |

几点说明：
- **h120、h160、h200 是同一类。** SDK 记录的攀越状态都是 4，sweet spot 都是 0.78；h100 是状态 5（0.73），h80 是状态 6（0.65）。
- **接近方式不影响曲线。** 冲刺、走路、斜 30° 的曲线重合；走路只改变出口速度（199.5）。
- **视线偏 45° 会让曲线变矮**（峰值 3.2°），开窗提前约 0.04 s。原生动画按接近角度混合（`m_traversalYawPoseParameter`），这里看到的就是它的效果。
- **准心俯仰不影响曲线。** p0、pm30、pp30 在 h120 上的开窗进度是 0.77 / 0.77–0.78 / 0.76–0.77。所以 δ 是动画给的偏移，不是"玩家必须看向某处"。
- **蹲姿 h120 有两种。** 有时时长 0.65 s（状态 7），有时 0.81 s（状态 8）。长的那种 δ 很小，后半段几乎都 < 1.5°，所以窗口由"进度 > 0.5"决定，宽到 0.47 s。哪一种取决于蹲下动作在攀爬开始时是否已经完成。

## 5. 和原生超级滑铲对照

| | 原生超级滑铲（S21） | Mantle boost（S27，SDK 移植） |
|---|---|---|
| 开关 | 原生 | `mantle_boost_enabled`（Flowstate 默认开） |
| 判定 | 时间：攀爬最后约 0.085 s 内按跳，下一帧按蹲（M8） | 角度：δ < 1.5°、正在回落、进度 > 0.5 |
| 窗口 | 约 0.085 s | 站姿约 0.13–0.19 s；蹲姿长可到 0.47 s |
| 出口 | 460 / 286 | 388.7 / 367.42 |
| 按法 | 跳 + 蹲 | 只要跳（跳 + 蹲也一样） |
| 两者同时开 | — | boost 先判定，超级滑铲拿不到 460 |

## 6. 局限

- 每类样本少：蹲姿各 2–6 次，h80 / h100 各 4 次。站姿 h120+ 有 36 次，是最可靠的一类。
- h60 以下、h200 以上、斜向的其他角度（只测了 30° 和 45°）都没有测。
- 曲线来自渲染视角，末尾和判定值差约 0.3°（§4.3）；开窗时刻（δ 从 1.5° 往下）不受影响。
- 这是社区对 S27 的移植。阈值 1.5°、出口 ×1.3 和 90 u 都是 SDK 作者定的，不保证和官方 S27 一样。

## 7. Unity 复刻方案（HSD-Unity 分支 B1）

1. **每类一条 δ(进度) 曲线**，取 §4.3 的平均表，末尾当作 0。
   - 选类：站或蹲，加上攀爬高度（Unity 的 `mantleRise`；h80、h100、h120+ 三档）。
   - 视线和墙面法线的夹角在 0°–45° 之间时，用"站 h120+"和"偏 45°"两条曲线插值。
2. **判定**：照搬 §2 的 2–4 条，阈值 1.5°，进度 > 0.5。出口用现有的 `MantleBoost.ExitVelocity`。
3. **镜头**：攀爬时把 δ 加到 Native 镜头的俯仰上，屏幕上看到的就是动画镜头在抬头再回落。
4. **圆环**：用 §3 的同一个公式，在准心处画 1.5° 的圆环和偏移 δ 的中心点；标签 "BOOST"，判定后按结果变色。
5. **作为新的超级滑铲模式**（`SuperglideMode.MantleBoostS27`），默认值不变：Native 仍是参考模式。

几点约定：
- **类别的高度分界**用 Unity 的攀爬高度差（`mantleRise`）：< 39 是 h80 类，< 63 是 h100 类，其余是 h120+ 类。
  - 依据：R5 三类的时长 0.313 / 0.467 / 0.571 s，代入 Unity 的拟合 T = 0.173 + 0.0055·rise，得到 rise ≈ 25 / 53 / 72，分界取中点。
- **蹲姿 h120+ 用长的那条**（R5 8 次里 6 次是长的）。
- **只在游戏里开**：
  - 配置、回放、测试仍然用各自的模式（Reference 是 Native）；
  - 演示和 smoke 也保持原生超级滑铲。
- **测试**：
  - `MantleBoostS27Tests`：每一类的开窗进度和实测一致，站姿窗口是最后 0.125–0.16 s，判定顺序和 R5 的按键记录一致；
  - `A2Climb.S27ModeBoostsInsideTheAngleWindowOnly`：H232 窗口内按跳得到 388.7 / 367.41；跳 + 蹲也是 BOOST；早按是 FAILED，出口 299 / 289.82。
- **结果**（HSD-Unity `B1` fa9f1ca）：
  - EditMode 2041 / 2041，PlayMode 1 / 1；
  - M2 / M1 / M3 / M4 回放逐字节一致（只有生成时间不同）；
  - smoke 238 / 238，圈速 79.12 s（和 N7 相同）。
  - 构建在 `HSD-Build\B1\HSD-Practice.exe`。
- **试玩时看什么**：
  - 圆环合上（变成琥珀色）的时机和 R5 比，感觉是否一样；
  - 镜头在攀爬时先低头再回正，幅度是否合适（站姿 h120+ 峰值约 4.8°）；
  - 蹲姿高墙的长窗口（约 0.47 s）是否太宽松。
  - **这些曲线和分界都是实测平均值或设计值，还没有试玩过。**

## 9. 调参后不失效（B1-H，用户 2026-10-24）

用户试玩 B1 后觉得手感不错，并提问：以后调整数值，这套会不会失效？

**不会跟着失效的部分**：
- 窗口用攀爬进度表示，不用秒数。攀爬时长改了，窗口跟着缩放。
- BOOST 速度从当前参数算出（姿态速度 × 加速系数 + 跳跃高度）。
- 圆环自己算中心，不受镜头强度影响。
- 判定阈值（1.5°、进度 0.5）是 SDK 常数。

**原来的两个弱点和改法**：
1. **类别分界原来写死在高度上**（rise 39 / 63），是按当时的攀爬时长公式手算的。
   - 改法：分界改成按攀爬时长判断。存的是 R5 三类的实测时长 0.313 / 0.467 / 0.571 s，取中点 0.390 / 0.519 s。
   - 每次攀爬用自己的 T 选类（`MantleBoostS27.ClassifyByTime`）。
   - 这样无论 `mantleTimeBase` / `mantleTimePerUnit` 怎么调，每类窗口的秒数都保持 R5 的长度。
   - 在 Reference 的公式上，分界等于 rise 39.5 / 62.9（原来 39 / 63）。
2. **原来没有测试读取当前参数**：B1 的测试用的是 R5 的时长，演示、smoke 和圈速都关着 BOOST。
   - 新增守护测试：
     - `TheClassFollowsTheMantleTiming`：三组时长参数下，选类都跟着时长走；
     - `TheLiveConfigsKeepTheStandingWindowInTheR5Range`：Reference 和 Fun 的当前参数下，探测允许的每个攀爬高度，站姿窗口都在 0.09–0.18 s（R5 0.119–0.158）；
     - `TheLiveConfigsKeepACrouchedWindowOfAtLeastTwoCommands`；
     - `A2Climb.S27WindowSitsWhereTheCurveSaysOnTheLiveMantle`：真实攀爬（Reference 和改过时长的版本）里，窗口内两帧按跳是 BOOST，窗口前两帧是 FAILED；BOOST 速度等于失败跳的姿态速度 × 加速系数。
   - 以后改数值，只要让 BOOST 失效，这些测试就会失败。

**已知差别（没改，等用户决定）**：
- R5 的蹲姿攀爬更长（0.517 / 0.625 / 0.813 s），Unity 的攀爬时长不分站蹲。
- 所以 Unity 里蹲姿窗口的秒数比 R5 短，例如蹲姿 h80 约 0.05 s，R5 约 0.09 s。

## 2. K-5 起跳镜头 [native + Frida + 实测]

### 2.1 原生

- 原生跳跃 `0x140a3b550`（N1 名里含 `rumbleOnJump` 的那个调用点）：普通跳（地面、滑铲）调 `0x140a349c0`，"superjump"（二段跳）调 `0x140a34c00`。
- `0x140a349c0` 的写法和落地 kick（`Land_ViewKick` 0x140a35750）完全一样：三个随机数，种子 = SeedMix(命令随机种子, 盐)，盐 0x76704a58 / 59 / 5a（落地是 0x76704c58 / 59 / 5a）；写入第一组弹簧速度（玩家 +0x243c 俯仰 / +0x2440 偏航 / +0x2444 横滚）和第二组（+0x2454 / 58 / 5c，× 0.2）。
- 值：俯仰 (2 + r₁)·20，偏航 r₂·20，横滚 (0.9 + 0.5·r₃)·20。和落地 kick 不同：**和速度、滞空无关**，横滚总是正的（向右倾）。
- 二段跳 `0x140a34c00`（盐 'vDJX…'）：俯仰 (4.5 + r₁)·20，偏航 r₂·20，横滚 2·r₃·20。HSD 的 Octane 跳板二段跳反馈是 F7 的设计值（1.2°），没有改，见 §7。

### 2.2 实测

- CAM2_A Frida，18 次起跳：第一组 punch 俯仰峰值 1.79–2.87°（0.0642 × 速度，速度 28–45，公式 30–50），第二组 = 0.2 × 第一组，合起来 2.1–3.5°；横滚 1.0–1.6°。眼睛角度（`bP`）和翻越阶段（`tvP`）全程 0。
- 长滞空（232 u 岩石顶上跳下，滞空 1.26 s）：形状一样，0.6 s 回到约 −0.5°，之后到落地前保持在 0 附近。F6 记的"0.57 s 向上约 1.7°、跟着跳跃弧线"不是真的：**F6 的指标把基准取在 usercmd 的 TAKEOFF 那一帧，而 R5 的镜头时间线比 usercmd 早约 0.04 s，kick 在下一帧就开始了，基准已经在 kick 里面**（§6）。

### 2.3 Unity

- `R5MotorV2.jumped`：这条命令走了原生跳（`CheckJumpButton`，不含跳板等 launch）。只给镜头读，电机输出不变。
- `NativeCameraFeedback`：在跳跃命令上按 §2.1 加冲量，随机数用 `R5SharedRandom`（新盐 `SaltJumpPitch / Yaw / Roll`）；新增 `punchYaw` / `punch2Yaw` 两个偏航轴（落地 kick 的偏航是 0，所以以前不需要），偏航加在镜头偏航 kick 里（高度强度）。
- 对照（CAM2_C 15 个片段，R5 / Unity）：原地跳 2.65 / 2.67、3.17 / 3.20、3.40 / 3.27；滑铲跳 3.79 / 3.66、3.43 / 3.57、2.98 / 2.83、2.39 / 2.52；起跳横滚 1.33 / 1.32、1.63 / 1.62 等。对照重放用 R5 的命令号，所以随机数和 R5 一样。

## 3. K-6 翻越镜头 [native + Frida + 实测]

- CalcView 里 `GetTraversalViewPosition`：第一人称代理在翻越动画里（序列号 0x245–0x250，`traversal_anim`、`view_offset_entity_enable` 打开）时，镜头位置和角度取动画的两个镜头挂点；翻越结束后按 `traversal_viewLerpOut*` 淡出。动画数据在模型里，不在代码里，所以只能用实测曲线。
- Frida（CAM2_B，120 u 墙 8 次）：翻越阶段俯仰 0.37 → 3.0 → 4.9 → 4.9 → 3.4 → 1.5 → 0.2 → 0（每 0.08 s），峰值 4.86–5.01°；同时起跳 punch 照常在走，两者相加。翻越结束时**没有落地 kick**（不是下落着地）。
- 这正是 B1 量的"翻越镜头角度差 δ"（`MantleBoostS27` 的曲线，按 h80 / h100 / h120 / 蹲姿分类，和瞄准角无关）。B1 当时只在 S27 模式里用它；原生是每次翻越都有。
- Unity：`traversalCamera` 打开时，所有翻越都按这条曲线加俯仰（类别、偏航修正都沿用 B1）。
- 对照（B1 的 `_none_` 片段，峰值 R5 / Unity，到峰值时间）：h80 冲刺 6.0–6.9 / 7.4–7.8（0.32–0.33 / 0.32 s），h100 冲刺 5.2–6.3 / 5.9–6.2，h120 冲刺 4.5–5.3 / 4.6，h160 冲刺 5.3–5.5 / 4.6，h200 冲刺 5.3–5.8 / 4.8（1.11–1.12 / 1.11–1.15 s）；站姿的时刻都对上，峰值差 ±1°。h60 R5 不翻越、Unity 也不翻越，两边都只有起跳 punch。
- 蹲着翻越差得多：h120 蹲 R5 峰值在 0.52–0.60 s，Unity 在 0.29 s；h160 蹲 R5 0.99 s，Unity 没有驼峰（窗口里取到的是起跳 punch 的尾巴）。这是 B1 已知的"蹲姿翻越时间"问题，CAM2 没有动。

## 4. K-7 滑索复测 [native + Frida + 实测]

### 4.1 两次会话为什么不一样

- **N6 的滑索片段根本没上绳。** 对照里的 `N6_camera_m9zd_*` 6 个片段，R5 的原点一直在地面（z 294.92 不变），眼高 70，横滚一直是静止时的 −0.0439°。所以"N6 没有横滚、眼高 70"是没上绳的结果，不是滑索数据。（N6 真正的滑索会话 `N6_camera_zip` 当时也测到了横滚：转开 30° 时 1.0–2.3°，60° 时 −4.5 … +4.7°。）
- N10 的 5 个片段是对的。
- 也不是混合版本或分支问题：Frida 再次确认 S21 滑索全走分支 A（`maxCameraRoll` 只在分支 B 里用）。

### 4.2 原生

- 横滚（`Zipline_CameraRoll` 分支 A）：用**水平投影**找绳上点（只看 x、y 求参数，再取三维点），也就是"头顶正上方"的那一点；然后和钩爪横滚同一个公式（视角 30–50°、强度 0.7、封顶 25°）。绳子在正上方时横滚是 0，所以横滚大小完全取决于眼睛相对绳子的左右偏移。
- 眼睛偏移（`0x140b110c0` 写玩家 +0x2f78，CalcView 的眼睛位置函数 `0x140af24b0` 把它按"水平前方 / 左 / 上"加到眼睛上）：
  - 基础目标是 0（setfile `ziplineViewOffset` −16 −6 0 只在另一种滑索状态用，S21 绳子不走）；
  - 绳子挂在运动实体上时（`0x140749e20` 返回非空；我们测的脚本绳子是这样）加噪声：前后 5·N(x, y, z′)、左右 5·N(z′, x, y)、上下 5·N(y, z′, x)，上下大于 −4 时改成 −8 − 它；x、y、z = 原点 × 0.001，z′ = z + 0.02 × 游戏时间；
  - N 是 Ken Perlin 的 improved noise，置换表（`0x14167c490`）和 Perlin 的参考表逐项相同；
  - 每帧按 SmoothCD（ω 4）逼近目标，下绳后目标 0。
- 所以眼高从 70 慢慢降到约 61（目标约 −9），一次 1–2 s 的滑行到不了底；F6 记的 65.5 就是滑行中途的值。

### 4.3 实测

- CAM2_A Frida 4 次滑行：偏移上下 0 → −1.8（0.2 s）→ −4.3 → −6.2 → −7.5 → −8.3 → −8.6（1.2 s）；左右 −0.04 … −1.43 u（每次不同，随时间漂）；横滚目标 −0.2 … −2.4°，平滑后的绳子横滚跟着它。用 MoveDiag 的游戏时间和原点代进噪声公式，目标上下 −9.5 … −9.6，左右的走向和实测一致（差一个几秒的时间基准）。
- 下绳时还有一个很大的 punch（见 §7 K-8）。

### 4.4 Unity 和对照

- Unity：`zipViewOffset` 按 §4.2 实现（`PerlinNoise`，时间用会话时钟 + `noiseTimeOffset`；对照重放时设成 R5 片段开头的游戏时间 `t0_game`）；`zipRopeHorizontal` 绳上点改水平投影。
- 对照（N10_zip 5 个片段，R5 / Unity）：横滚峰值 −1.32 / −1.28、−1.44 / −1.41、0.28 / 0.34、−0.69 / −0.65、−0.92 / −0.88；结束时横滚同样差 0.01–0.08°；眼高 65.70 / 65.70、65.88 / 65.87、65.47 / 65.57、65.54 / 65.54、65.58 / 65.58。滑索 10 / 10 一致（改前 2 / 10）。
- 对照规则（`camera_compare.py`）：R5 从没离开地面的滑索片段（N6_camera 那 6 个）不算；R5 在指标窗口里已经下绳的片段不算滑索横滚（窗口里有下绳 punch，Unity 没有）。

## 5. 多个镜头动作同时触发时：R5 怎么合成 [native + 实测]

第一人称镜头每帧在 CalcView（`0x1407f2bb0`）里按这个顺序拼出来：

1. **眼睛位置** = 原点 + 视角高度（下蹲比例）+ 冲刺视角偏移 + 滑索视角偏移。都是相加。
2. **眼睛角度** = 瞄准角（准星就是这个，后面的都不改准星）。
3. 观看实体（过场 / 处决等）按比例 slerp 过去——这是唯一"覆盖"式的项，移动里用不到。
4. **翻越动画镜头**（`GetTraversalViewPosition`）：只在翻越时，把动画镜头的角度加上去（淡出也是加）。
5. **rodeo 平滑**（`0x1407f0de0`）：只在 rodeo 时。
6. **punch**（`0x140af1ed0`）= 第一组弹簧角度 + 第二组 ×（1 − 开镜比例）+ 武器 view drift。**所有 kick 都是往同两组弹簧里加速度冲量**：落地、起跳、二段跳、跳板、重力炮、墙跑开始 / 超时、抓墙、下滑索……同一条命令上有两个就两个都加，前一个还没衰减完的继续衰减，弹簧是线性的，所以就是简单相加。没有优先级、没有互相取消。
7. view drift 等（跑步晃动也在 punch 之后的这一段，不在 punch 弹簧里）。
8. **横滚**（`View_CalcRoll` `0x140afc480`）：
   - 侧移横滚（`sv_rollangle`，S21 是 0）+ 墙跑项（S21 墙跑关）+ 闪避项 + 滑铲倾斜 + 冲刺转向倾斜 + 绳子横滚 + 已经在角度里的 punch 横滚，**全部相加**；
   - 绳子横滚三选一：钩爪激活时用钩爪，否则在滑索上用滑索，否则摆荡；三者共用一个平滑状态（N12），切换时不跳变；
   - 和按 360° 取模、折回 ±180°。**没有 40° 上限**。`maxCameraRoll` 40 只在滑索分支 B 里封它自己那一项（S21 不走分支 B）。各项有自己的上限：滑铲 15°、冲刺 2°、钩爪 20°、滑索 25° × 0.7。

所以 CAMERA-REFERENCE §3.9 原来写的"限制在 ±40°"不对，N12 写的"折回 ±180°"是对的（§3.9 已改）。

### 5.1 实测的组合

- 滑铲跳的落地：Unity 的落地 kick 本身就比 R5 大（改前就是，绝对值 1.7–2.0° 对 1.1–1.3°）；改后指标多出的 0.2° 是起跳 punch 的尾巴让"落地前一帧"的基准低了 0.2°（R5 那一帧也在 punch 尾巴里，只是 R5 低得少）。落地 kick 大的原因没查（可能是滑铲落地的下落速度或滑铲续接），记为待定（§7）。
- 翻越结束不触发落地 kick（Frida 8 / 8）。

## 6. 指标的修正（`research/feel/camera_compare.py`）

- **起跳对齐**：R5 的镜头时间线比 usercmd 早约 0.04 s，起跳 kick 在镜头的离地帧之后一帧就开始。K-5 / K-6 指标改成用每个身体自己镜头上的离地帧（地面 1 → 0）做起点和基准，和落地本来的做法一样。
- **落地 kick 回零时刻**：落地前 1.5 s 内起过跳的，回零按起跳前的水平算（落地前一帧在起跳 punch 的尾巴里，两边都差零点几度）。
- **滑索**：见 §4.4 的两条排除规则。
- 这些改动只影响 K-5 / K-6 / 滑索 / 落地回零几行；其余指标算法不变。

## 7. 新发现、没改的（等用户决定）

- **K-8 下滑索 punch**：`0x140a35ac0`（`rumbleOnZiplineDetach`）下绳时俯仰 (10 + 3·r₁)·20、偏航 10·r₂·20、横滚 10·r₃·20，实测第一组峰值 12–14° 向下、横滚 ±1–5°。Unity 没有。
- **二段跳 punch**：`0x140a34c00`，俯仰 (4.5 + r₁)·20（约 3.9–6.2°）。HSD 的跳板二段跳现在是 F7 设计的 1.2° 小凸起；要不要换成原生值。
- **滑铲跳落地 kick**：Unity 比 R5 大约 1.5 倍（改前就是），原因没查。
- **蹲姿翻越镜头时间**：见 §3（B1 的蹲姿翻越时间问题）。
- **K-6 指标的一个平局**：`B1_h200_b1_cr_none` r9603 的"翻越峰值时刻"由一致变成不一致。0.25–1.2 s 窗口里 R5 的最大值是 0.25 s 处起跳 punch 的尾巴（2.92°），翻越驼峰（2.72°，0.96 s）只差 0.2°；Unity 改后两者也几乎一样高，取到了驼峰。改前"一致"是因为 Unity 那时整段都是平的。没有调。

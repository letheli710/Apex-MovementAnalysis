# R6 斜坡滑铲：上坡、缓坡、坡度变化、横向（R5 实测 + Unity Reference 对照）

R5Flowstate S21 本地离线，Gibraltar，120 fps。4 个会话，**133 次有效试验**，27 个条件，每个条件 ≥ 5 次。另做了 Unity Reference 对照：用同样的 R5 输入、同样的坡面几何。证据等级：**[meas]** 实测，**[native]** 原生代码（Ghidra），**[fit]** 拟合，**[inf]** 推断。

决定和日志由主控记，这份文档不改 `DECISIONS.md`。

## 结论先行

1. **原生公式在所有测过的情况下逐命令成立** [meas + native]。滑铲贴地时，每条命令的水平速度变化是：水平速度 += g·dt·n_z·n_水平（g = 750）；摩擦和平地一样，是 (s − D·dt)·0.7^dt。D 的取值：按住下蹲时 100，松开下蹲时 400。
   - 覆盖：5–40°，上坡、下坡、横向、斜向，按住或松开下蹲。
   - R5 残差 rms 0.001–0.19 u/s。
   - 沿坡额外加速度 = 750·sinθ·cosθ：5° 65、10° 128、15° 187、20° 241、25° 287、30° 325、40° 369 u/s²。
2. **缓坡没有坡度门槛** [meas + native]。5° 的实测是 65.1 u/s²，原生公式给 65.1。
   - M8 的拟合 147 + 342·sinθ 只在 29–41° 成立。坡度越缓偏差越大：5° 时它给 177，实际是 65。这条拟合作废，以原生公式为准。
   - 每个坡度有一个平衡速度 v_eq = (750·sinθ·cosθ − 100)/0.357。
     - 5° 和 10° 的 v_eq 低于 125，滑铲会慢慢减速直到结束（5° 在坡上 2.27 s 后结束）。
     - 15° → 245，20° → 395（实测停在 398），25° → 525，30° → 630。
3. **上坡**：滑铲按同一个公式减速，减到 125 u/s 结束。**不会倒滑** [meas]。
   - 结束后：按住 W 变成 92 u/s 的蹲走，继续上坡；不按 W 就在原地停住（速度 0，位置不变）。
   - 从坡脚以约 400 u/s 冲上坡（10/20/30/40°）：坡上滑行 0.87 / 0.64 / 0.53 / 0.49 s，沿坡上行 222 / 165 / 136 / 124 u。
   - 滑铲跳以约 258 u/s 落到坡上（落点在坡脚以上 38–72 u）：落地就接着滑铲，坡上滑行 0.46 / 0.33 / 0.28 / 0.25 s。
   - 滑铲中松开 W 和冲刺键，减速不变（`_rel` 和 `_slide` 两组完全一样）[meas]。N2-S 里写的"D = 100 需要按住下蹲且向前"，其中"且向前"不成立。
4. **坡度变化处不会飞起来** [meas]。133 次试验在所有转折处，前后 0.3 s 内离地命令都是 0，滑铲状态也不中断。
   - 测过的转折：平地→下坡 5–30°（403 u/s）、下坡→平地（25° 时 414、30° 时 566 u/s）、V 形 −20°→+20°、坡顶 +10°→−20°（滑铲 287 u/s，冲刺 299 u/s）。
   - 冲刺在坡上始终是 299 u/s。
5. **新发现：换地面实体时滑铲再加速一次** [native + meas]。
   - 原生机制：`SetGroundEntity`（0x140a51650）在地面实体变化、且下蹲状态为 1 或 2 时，调用 `Slide_TryBegin`。`Slide_TryBegin` 不检查"是否已在滑铲"，所以距上次滑铲开始超过 2 s 就再给一次加成：min(h + 172.5, 约 460)，同时把计时重置。
   - 实测：在两块砖的接缝、V 形谷底，滑铲开始后 2.10–3.49 s 都出现了 398→461、301→461、255→428。在 2 s 内过接缝的（dn25、dn30、对角下坡）没有加成。
6. **横向和斜向**：按向量公式，速度方向会往下坡转 [meas]。
   - 横向（沿等高线、20° 坡）：航向从 90° 转到 24°，滑铲 3.15 s。
   - 斜向下坡（45°）：一直在加速。
   - 斜向上坡（135°）：1.05 s 后在 125 u/s 结束，航向转到 96°。
7. **和 Unity Reference 对照**：逐命令的坡面公式一致（Unity 残差 rms ≤ 0.005），上表里大部分现象也一致。不一致的是 3 处主要差别和 2 处小差别，见下一节，并已按 D-36 写成修改建议（只写建议，没改 Unity）。

## 方法

### 坡面几何（`--geometry r6slope`，[../tools/slope_geo.py](../tools/slope_geo.py)）

M8 用的是靶场旁边的天然山坡，坡度 29–41°，大小不规则，做不出指定坡度和转折。所以这次自己搭。

- **地点**：靶场北边地图外的虚空（y ≥ 24000，x −12000…12000），z 3000。
  - 用射线查过：z 16000 到 −30000 之间什么都没有。
  - 在那里站 20 s 不会被判出界。
  - 靶场平地本身只有约 1000×1500，上空 3000–6000 有岩拱，放不下。
- **砖块**：`mdl/canyonlands/firing_range_towerblock_01.rmdl`。
  - 射线测过：碰撞是一个方盒，顶面在原点上方 512.03，半宽 511.5（±511 有命中，±512 没有）。
  - 地图编辑器目录里，这个模型的掩码包含靶场那一位，所以晚加载不会卡死服务器。不在掩码里的模型会让 dedi 挂住，这次试过一个 `thunderdome_cage_ceiling_512x128_04` 就挂了。
  - 另外两个模型不能用：`tday_vtol_landing_pad_square_01` 只有外框有碰撞，`landing_pad_tarmac_nobase` 的碰撞是圆盘。
- **铺法**：一条道 = 沿 +X 的一串平面段。每段用共面的砖铺，pitch = −坡度（pitch +p 时顶面沿 +X 下降）。
  - 凸转折（平地→下坡、坡顶）两边的砖必须正好对齐。
  - 凹转折处允许一边伸到另一边的面下面。
  - 46 块砖铺完后，用射线逐条核对：13 条道的表面和设计误差都 < 0.6 u。
- **13 条道**：
  - `up10/20/30/40`：一块平地，接一块上坡。
  - `dn5/10/15/20/25/30`：顶部平地，两块下坡，底部平地。
  - `v20`：平地，−20°，+20°。
  - `crest`：平地，+10°（500 u），−20°（两块），平地。
  - `lat20`：一个 20° 坡，沿坡两块、横向三块。

### 试验（[../tools/hsd_trial.py](../tools/hsd_trial.py) 的 `r6_*`）

所有条件都是先冲刺 1 s，再按下蹲开始滑铲。按住下蹲 3–5 s 后松开，见 `_R6_SLIDE`。

| 后缀 | 做法 |
|---|---|
| `_slide` | 按住 W、冲刺键和下蹲 |
| `_rel` | 滑铲开始 0.25 s 后松开 W 和冲刺键，下蹲继续按住（看无输入时会不会倒滑） |
| `_jump` | 滑铲开始 0.15 s 后跳，下蹲一直按住，落在坡上 |
| `_duckup` | dn30 在 1.2 s、up20 在 0.3 s 时松开下蹲 |
| `crest_run` | 只冲刺，不滑铲 |
| `crest_slide` | 冲刺 2.3 s 后在坡顶前按下蹲 |

起点是第一个转折前 330 u（`_jump` 是 400 u）；`lat20` 的起点在坡面上（复位时 `PlantOnGround`）。试点会话 `R6_pilot`（每个条件 1 次）用来校准：起点从 520 u 改到 400 u，原来那个起点落地在坡脚前 34 u。

### 分析

- [slope_load.py](slope_load.py) 和 [slope_to_trial.py](slope_to_trial.py)：用 a2_load 读每条客户端首次执行的 usercmd，写成 hsdmove-trial/2 格式，带 `world.slope_segments`。
- [slope_analysis.py](slope_analysis.py)：R5（samples.csv）和 Unity（reference.csv）当成同一种逐命令数据流，算同一套指标：逐命令原生公式残差、额外加速度、移动比例、上坡、转折、二次加成、横向。
- [slope_table.py](slope_table.py)：把结果整理成表。

逐命令检查只取这样的命令：贴地、在滑铲中、前后在同一个平面段上、离转折 ≥ 24 u。速度跳升 > 20 的（二次加成）单独统计。

### Unity 对照（为什么不用 FeelBatch）

`FeelBatch` 和 `FeelReplay.World` 的世界只有三样：地面高度、一个墙盒、绳索。不能放坡道，现有的场景参数也做不到。而 HSD 的 `MovementWorld.AddRamp` 是支持坡道的。

所以写了一个独立的 dotnet 工程 [harness/](harness/)：

- 只读地编译 `HSD-Unity/Assets/HSD/R5Replay/Runtime` 的源码。
- 用 `AddRamp` 和盒子搭出同样的道。
- 按 `FeelReplay.GameBody` / `Run` 的同一套步骤，驱动 `MovementConfigs.Reference()` 的游戏身体：同一个技能组合，每条命令同样的输入，按行拆成子步。

没有改 HSD-Unity 的任何文件，也没开 Unity 编辑器。编译产物放在仓库外。

```
dotnet build research/phase2-local/slope/harness -c Release -o <out>      # 读 ../../../../../HSD-Unity，可用 -p:HsdUnity=<path> 改
```

所以对照的是 Reference 的运动核心（R5MotorV2 + MovementWorld），Unity 渲染和输入层不在范围内。HSD-Unity 的 `R5Replay/Runtime` 源码和 `c0d92cd`（F6 合并后的 main）完全一样（当时工作区在另一个会话的分支上，只有一个 README 不同）。

## 原生代码

- `Gravity_HalfStep`（0x140a36130）：滑铲标志（0x2d75）开着、地面实体有效（0x324）时，水平速度 += 半步 g·dt·n_x·n_z，n_y 同理（n 在玩家 0x43dc–0x43e4）。没有坡度条件，也不看下蹲键。移动前后各一个半步。这就是 N4D 的 S-09，这次在 5–40°、上下坡、横向都逐命令验证过。
- `Slide_TryBegin`（0x140a54890）：只检查水平速度、地面法线 n_z > 0.7 和视角点积，**不检查是否已经在滑铲**。冷却到了就加成，并且无论有没有加成，都更新"上次开始"的时刻。
- `SetGroundEntity`（0x140a51650）：地面实体变化、新地面不为空、并且下蹲状态 0x2a70 ∈ {1, 2} 时，调用 `Slide_TryBegin`，第三个参数是"之前在空中"。这就是二次加成的来源（U-3）。
- 调用 `Slide_TryBegin` 的只有 `Duck`（两处）和 `SetGroundEntity`，用 `RefsToAddrs.java` 查的。

反编译文本含游戏代码，只留在本地，没有提交。重跑用的是持久工程：

```
analyzeHeadless <ghidra-projects> r5apex_dx12 -process r5apex_dx12.exe -noanalysis -readOnly -scriptPath research/rea-native/n2 -postScript DecompileList.java <list> <out.c>
analyzeHeadless ... -postScript RefsToAddrs.java <out.tsv> 140a54890
```

## 限制

- 只测了 Gibraltar、120 fps、一个滑铲入口速度（坡脚约 400，滑铲跳落地约 258）。
- 没有测 < 5° 和 > 40° 的坡。超过 45.6° 不能站（n_z ≤ 0.7）。
- 转折最大测到平地 → −30°（403 u/s）和 −30° → 平地（566 u/s）。更大的折角、更高的速度会不会离地没测。
- 坡道全由道具拼成，所以每个转折和接缝都同时是"换地面实体"。在 Apex 的地形上，同一实体内部的坡度变化不会触发 U-3；这一点是推断，没测过。
- U-2 只测了静止和滑铲中原点在坡上的高度，碰撞体的具体形状没有读原生代码确认。

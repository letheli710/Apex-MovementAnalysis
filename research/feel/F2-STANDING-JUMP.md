# F-2：原地跳 Unity 比 R5 高 1.8 u，查清了

2026-10-28。用户："检测是不是底层上导致的，如果不是记录一下就好"。

**结论：不是移动代码的问题（结果 A）。Unity 没改。**

R5 那一次跳得矮，是跑测试的工具造成的。每个片段开始前，工具在 dedi 上把玩家重置到起点。dedi 把这次重置算成了一次"落地"。0.72 s 后起跳时，原生的"刚落地又跳要矮一点"规则（`antiMultiJump`）在 dedi 上生效，把跳跃高度压低了。客户端预测不知道这次落地，所以按完整高度跳。几条命令以后，客户端被 dedi 的结果纠正，录下来的轨迹就矮了。Unity 两套电机的结果和客户端预测一样（片段开头的重置不算落地），所以看起来比 R5 高。

真正玩的时候不会有这种重置，所以按 Unity 现在的规则就对。

## 1. 数据

| | `e4_stand_r351` | `e4_stand_r352` |
|---|---|---|
| R5 最高点（离地） | 53.99 u | 53.20 u |
| Unity 回放电机 / Reference | 54.97 u | 55.00 u |
| 差 | +0.98（在容差内，记"一致"） | **+1.80**（F-2） |

FEEL.md 里的"R5 51.2 对 Unity 53.0"量的是从第一个空中采样点算起的高度（R5 那一点已经离地 1.98 u）。换成从地面量，差值不变。

## 2. 逐条排查

| 候选原因 | 结果 |
|---|---|
| 起跳速度和时刻（同一条命令？在重力前还是后？） | 一样。原生 `Jump`（0x140a3b550）在起跳命令里加 `sqrt(2·g·H·frac)`，再走半步重力，离地后的速度是 V − 1.5·g·dt。客户端预测 282.014，Unity 281.998（dt 6.96 ms，差 0.02 u/s） |
| 重力积分（开头半步、结尾半步） | 一样。Unity 每条命令正好 750·dt；R5 每条命令也是 750·dt，只有被纠正的那一条例外（下一行） |
| 起跳时贴地、台阶 | 一样。第一条空中命令后 z = 296.897（R5）对 296.901（Unity） |
| 量的是原点还是眼睛 | 两边都是原点 `pos_z` |
| 帧率和命令边界 | 回放按 R5 记下的每条命令的 dt，命令一一对应 |
| 采样漏掉真正的最高点 | 最高点那一帧竖直速度 1.6 u/s，最多漏 0.002 u |
| **客户端和 dedi 不一样（混合版本）** | **原因在这里**，见 §3 |

## 3. 原因

在全部 99 次 R5 跳跃（M1–M3 + M4 的平地片段）里检查"每条空中命令的速度变化 = 750·dt"。只有这两次 M2 原地跳各有一条命令不符：

| | 起跳后第几条命令 | 速度多掉 | 位置 |
|---|---|---|---|
| r351 | 第 6 条 | 2.6 u/s（相当于多 3.4 ms 重力） | 反而少走 |
| r352 | 第 8 条 | 4.7 u/s（相当于多 6.3 ms 重力） | 反而少走 |

速度掉得更多、位置却走得更少，不是"这一帧更长"，而是被纠正了。原始日志（`20261020_205712_M2_rerun`，MOVE-TRACE 两边都有）证实：

1. 起跳命令 54760：客户端预测 vz 282.014，**dedi 算出 277.285**。
2. 命令 54766 起客户端带 `rp=1` 重新预测，起点是 dedi 的状态（306.042 / 251.237），不是自己原来的预测（306.239 / 255.965）。
3. 这个 session 的 5 次原地跳，dedi 每次都比客户端低 2.6–7.8 u/s，客户端每次都是 282.01。

dedi 为什么低：原生 `Jump` 在"距离上次落地 < `antiMultiJumpTimeMax`（0.75 s）"时把高度乘上 1 − 0.7·f。f 在 0.15 s 以内是 1，到 0.75 s 线性降到 0（`antiMultiJumpHeightFrac` 0.3）。落地时间由 `SetGroundEntity`（0x140a51650）在"空中 → 地面"时写进 player +0x3680。用 dedi 的起跳速度反推"距离上次落地"，和 dedi 日志里 `HSD-RESET` 到 `JUMP` 的间隔对得上，每次差不到 1 ms：

| 片段 | dedi 重置 → 起跳 | 用起跳速度反推 |
|---|---|---|
| 351 | 0.735 s | 0.734 s |
| 352 | 0.722 s | 0.722 s |
| 353 | 0.727 s | 0.727 s |
| 354 | 0.711 s | 0.711 s |

检查：从 dedi 的起跳状态开始，用同样的纯重力积分和 R5 记下的 dt 往下算，最高点是 53.990 / 53.201 u，和 R5 录到的 53.991 / 53.200 只差 0.001 u。

对照组：M4 的两次原地跳（`e4_stand_r1616` / `r1617`，120 fps）在重置后 0.849 / 0.840 s 才起跳，超过 0.75 s，没有惩罚，也没有纠正。R5 最高点 54.80 u，Unity 和它完全重合（路线偏差 0.0）。

推断（没单独验证）：重置路径在 dedi 上走到了一次 `SetGroundEntity`（空中 → 地面），所以写了落地时间。上一个片段的起跳留下的 +0x36a9 = 1 让惩罚生效。客户端没预测这次重置，所以落地时间还是几秒前的。

## 4. 影响

- Unity：不改。两套电机都有 `antiMultiJump`（真实落地后再跳会矮），片段开头的重置不算落地，这和真实游戏一致。
- 对照工具：原地跳片段重置后要等 0.75 s 以上再跳（M4 的片段已经满足）。M2 的 `e4_stand` 两条以后看到差 1–2 u 时，知道是这个原因就行，不用重测。
- 其他片段：99 次跳跃里只有这两次被纠正，别的结论不受影响。

## 5. 复查方法

脚本放在会话的临时目录，没有提交。思路如下：

- 每次跳跃逐条命令检查 `(vz_prev − vz) / 750` 是不是等于 dt。
- 用命令号把客户端和 dedi 的 MOVE-TRACE 配对，只取客户端第一次预测（去掉 `rp=1`）。
- 用 V' = vz + 1.5·g·dt 和 frac = (V'/√(2·750·56))² 反推时间：t = 0.75 − 0.6·(1 − frac)/0.7。

# F1：R5 手感对照（叠图 + 指标）

日期 2026-10-25。用户的想法（2026-10-25）：手感很难靠试来确认，Unity 也没有动画，所以改成"测试 + 指标 + 两边直接叠在一起比"。

## 1. 做法

同一串输入，交给三个对象，再用**同一套指标代码**分别算：

| 对象 | 是什么 | 来源 |
|---|---|---|
| R5 | 真值 | 已提交的 R5 实测片段 `samples.csv`（每个 usercmd 一行：输入 + 位置、速度、状态） |
| 回放电机 | 对齐 R5 的研究电机（M2–M4 回放一直逐字节不变） | Unity `Replayer.Replay`，参数 `R5MotorV2Params.FromTrial` |
| **Reference** | **练习游戏里实际玩的身体** | Unity `FeelReplay.GameBody`：`MovementConfigs.Reference().CreateBody(...)`，喂入 R5 记录的每条 usercmd |
| Fun | 设计版身体 | 同上，`MovementConfigs.Fun()`（只作参考，本来就和 R5 不同） |

- Unity 的输出由 `HSD.R5Replay.Editor.FeelBatch.Run` 写出：每个片段 `replay.csv`、`reference.csv`、`fun.csv`。
- `FeelReplay` 只做"把输入喂给游戏身体"。测试 `FeelReplayTests` 证明它和手动逐帧调用 `SkillBody.Step` 完全相同。
- 地面是平地（M1–M3 的跑道）。游戏身体用自己的武器速度系数，和实际玩一样。

## 2. 指标（`feel_metrics.py`）

每个指标按"每次出现"算：每次起跳、每次滑铲、每段稳定移动各一个值。

| 指标 | 定义 | 容差（一致） |
|---|---|---|
| 起跳水平速度 / 落地前速度 | 起跳那一帧 / 落地前一帧的水平速度 | 2 u/s 或 1 % |
| 跳跃高度 / 滞空时间 | 起跳到落地之间的最高点 − 起跳高度；起跳到落地的时间 | 1 u 或 2 % / 1.5 帧 |
| 滑铲峰值速度 / 时长 / 结束速度 | 每段滑铲 | 3 u/s 或 1 % / 3 帧或 3 % / 5 u/s 或 2 % |
| 地面稳定速度 | 每段 ≥ 0.4 s、全程着地、不滑铲的有输入阶段，最后 0.25 s 的平均水平速度 | 2 u/s 或 1 % |
| 加速到 90 % 用时 | 同一阶段，从开始到速度走完 90 % 变化 | 3 帧或 5 % |
| 停下用时 / 距离 | 松开输入后，水平速度降到 1 u/s 以下 | 3 帧或 5 % / 2 u 或 5 % |
| 空中转向角 / 速度 | 空中输入改变后 0.15 s 的方向变化和速度（Lurch、扫向） | 2° / 3 u/s 或 1 % |
| 结束时速度 | 最后一帧 | 3 u/s 或 2 % |

结论分四档：
- **一致**：在容差内；
- **接近**：在 3 倍容差内；
- **不一致**：更大；
- **次数不同**：例如 R5 跳了 4 次，对方只跳了 2 次。

起跳和落地按地面标志算（两边同一个定义；第二批起），翻越中的行算在空中。

另外逐帧算路线偏差（水平距离的均方根），以及起跳、落地、滑铲开始和结束的时间差。

### 3.1 F-1 的修改（HSD-Unity#35）

- 新开关 `R5MotorV2Params.slideDuckTransitionFromNextCommand`，Reference 打开，Fun 继承。回放电机不开，所以 M2–M4 回放不变。
- 打开时，滑铲的下蹲过渡（200 ms）从按下蹲的**下一条命令**开始算。所以 144 Hz 下：
  - 按下蹲后第 29 条命令（0.201 s）起跳：扣加成，约 248 u/s（R5 247.9 / 247.7）；
  - 第 31 条命令（0.215 s）起跳：不扣，约 405 u/s（N4-C 约 410；比 0.201 s 低一点只是滑铲多减速了两条命令）。
- 测试：`FeelReplayTests.ASlideJump0201sAfterTheDuckPressIsRefunded`、`ASlideJump0215sAfterTheDuckPressKeepsTheBoost`、`TheTransitionStartsOnTheNextCommandOnlyInTheConfigs`。
- 重跑对照后的结果见 §3.2。

4. 两批一起：`feel_compare.py <out>,<out2> phase2-local/m1/trials phase2-local/m2/trials phase2-local/m3/trials <trials_out> --export <dir>`（逗号列表里用 Windows 路径）。
5. `data/scorecard.json`、`data/trials.json` 提交；叠图用的 `series.json`（约 3 MB）、`series_climb.json`（约 5.5 MB）和转换出来的攀爬片段都可以重新生成，不提交。

## 6. 第二批：攀爬、翻越、superglide（F2，2026-10-26）

### 6.1 数据和做法

- R5 数据：本地原始会话 M6 A2b（h60–h400：爬、走、悬挂、取消、蹦、反向蹦）和 M8 r_sg（h90–h232：冲刺 / 走路 / 滑铲 / 斜向 / W+D 接近，翻越开始后第 K 帧按跳 + 蹲）。共 **494 个片段**。
  - `M8_sg_h120_fsm` 没用：那一场开的是另一种 superglide 模式。
  - 有 1 个片段丢了一帧，对不齐，跳过。
- `climb_to_trial.py` 把原始会话转成和 M1–M3 一样的片段格式：
  - **R5 在翻越过程中两边都不打印 usercmd**，命令编号会跳过一段（h120 约 63 条）。这段用同一时间的客户端帧补上：每帧一条，输入（跳、蹲、前进轴、视角）和位置都取帧上的。superglide 的按键正好落在这段里。
  - 每行加一个状态列：none / climb / mantle / hang，取自 [HSD-STATE]。
  - `trial.json` 加 `world`：地面高度和 A2 那面墙（一个盒子）。
    - 墙顶 = 地面 + H + 5.92，每场从翻越后站在墙顶的高度取中位数，和公式一致；
    - 墙面 x = −13704.5，每场接触时的原点 x 都在墙面 − 16 附近（±2 u）；
    - 厚度 208 u：R5 走下墙顶背面时原点在 −13481（108 次的中位数），等于边缘 + 16。
- Unity：`FeelReplay.World` 按 `world` 摆墙，`FeelBatch -trials <目录>` 批量读，每行输出 Unity 攀爬状态。回放电机没有墙，所以攀爬片段只比 Reference（和 Fun）。
- 指标：攀爬片段只评两边定义相同的量：
  - 翻越**结束**时刻；
  - 结束后第 2 条命令的水平出口速度（superglide 约 460，跳 299）；
  - 0.1 s 内最大竖直速度（有没有跳）；
  - 停下、结束速度、路线偏差。
  - 原因：R5 的翻越状态比接触晚几条命令才置位，R5 的攀爬阶段没有状态，并且攀爬时地面标志一直是 1，所以起跳次数和翻越开始时刻在攀爬片段里比的是标志，不是动作。

| | 一致 |
|---|---|
| 平地（第一批，现在用地面标志算起跳） | 511 / 513 |
| 攀爬 / 翻越 / superglide | **1957 / 2223（88.0 %）** |

- **一致的部分**：
  - 窗口中间的 superglide：112 个片段两边都是 460 u/s，竖直速度相同；
  - 不按跳的翻越结束时刻：A2 各高度中位数差 0–8 ms；

### 6.3 找到的差别（改 Unity 需要用户决定）

| # | 情况 | R5 | Reference | 原因 | 建议 |
|---|---|---|---|---|---|
| **C-1** | 滑铲跳接近 h120（15 个片段） | 碰墙时离墙顶 94 u，**立刻开始攀爬**，0.19 s 后翻越 | 碰墙后 **0.17 s 什么都不做**，掉到离顶 98 u 以下才开始攀爬，翻越晚 0.49 s；superglide 按键落在翻越刚开始，被"切到台面" | **Unity 的台沿探测有死区**：只在 80 u（翻越够得着的高度）以内找顶；找不到时，用"80 u 处能不能放下蹲姿身体"判断墙是太高还是太矮，而这个判断允许 18 u 的台阶。所以顶在 80–98 u 之间时被当成"太矮"，既不翻越也不攀爬 | 修 `MovementWorld.ProbeLedge`：顶在够得着的高度以上就判"太高"（攀爬）。影响所有游戏身体 |
| **C-2** | superglide 按得早（约 15 个片段，h90–h232） | 照样起跳（竖直约 285），但水平只有 **348–434 u/s** | 切到台面，不跳（299，竖直 0）；或者已经是完整的 460 | R5 在窗口前沿有一段"减量 superglide"；Unity 只有"切"和"完整"两档 | 先单独研究 R5 的减量规则（可能是当时的姿态速度 + 滑铲加成），再决定 |

| **C-4** | 走路接近 superglide（k59–k65，3 / 3） | **402**（J-1 的 +30 让走路速度过了 200，滑铲加成生效） | 200 跳 | J-1 的频率规则认为这几次没有先碰墙，清掉了表面法线 | 查这几次 R5 是怎么碰的墙，再调 J-1 的清除条件 |

**结论**：攀爬和 superglide 的主体（窗口中间、普通翻越、落地）和 R5 一致。差别在窗口两端、走路接近和滑铲跳接近。C-1 是明确的 bug，玩家滑铲跳上墙时就会碰到；C-5 很简单。C-2、C-3 要先补研究。

### 6.4 用户决定（2026-10-26）和处理

> 修 C-1（台沿探测死区）和 C-5（走路翻越出口 199.5），C-2、C-3、C-4 先补研究。

**C-1 已修（HSD-Unity#37）**：`MovementWorld.ProbeLedge` 判断"太高还是太矮"时改用严格的重叠检查（不带 18 u 台阶区）。
- 现在顶在够得着的高度（80 u）以上，一律判"太高"，开始攀爬；真正的台阶仍然判"太矮"。
- 影响所有游戏身体。回放电机没有世界，不受影响。
- 测试：`TheLedgeProbeHasNoDeadZoneAboveTheReach`（85 / 94 / 150 u）、`ATopWithinTheReachIsStillALedge`、`ABodyMeetingTheFace94uBelowTheTopClimbsAtOnce`。
- 连带改了两个 J-1 测试（`SuperglideM8BTests`）：
  - 它们原来的"先贴着墙往上滑"场景（离墙 30 u 起跳）其实就是靠这个死区。修好后身体在接触时就开始攀爬，和 R5 一样；
  - 每个起跳距离的结果都和 R5 的多数情况相同（走路 12 / 15 的普通翻越跳，斜向 15 / 15 沿视线）；
  - J-1 的推力改用"贴着墙原地起跳"检查（+30 u/s）。

**C-5 已修**：新开关 `ClimbParams.mantleExitWalkSpeed`，由 `MovementConfig.mantleExitWalkSpeed` 打开（Reference 打开，Fun 继承）。
- 翻越自然结束（没按跳）时，按住冲刺出口 299，没按住出口走路速度 173.5 × 1.15 = 199.525。
- 依据：R5 的 maxspeed 在走路接近时是 199.525，按住冲刺时不管怎么接近都是 299。
- 测试：`TheMantleEndLeavesAtTheStanceSpeed`。

**C-2 研究**：以"离自然结束还剩多久"排 R5 的所有 superglide 按键（冲刺接近 h90–h232，约 150 次）：

| 剩余时间 | R5 | Reference |
|---|---|---|
| 大于约 100 ms | 切到台面，299，不跳 | 切到台面 |
| 约 83–100 ms | **减量 superglide**：起跳（竖直约 285），水平 348–429，越晚越大；和"切"混在一起 | 小于 102.5 ms 就是完整 460 |
| 约 0–83 ms | 完整 460 | 完整 460 |
| 结束以后 | 普通跳 299（碰过墙是 329） | — |

- 减量的值像"当时的翻越前进速度 + 滑铲加成 172.5"：反推出的前进速度从约 175 涨到约 288。也就是 R5 用的姿态速度跟着动画走，不是固定 299。
- Unity 现在是一刀切：102.5 ms 以内完整，以外切。
- **用户决定（2026-10-26）：简化，不做斜坡。** 只要在这段时间里触发，就给固定值，按最佳时机算：完整 460。
  - Reference 现在就是这样：剩余 102.5 ms 以内都是 460，已经覆盖了 R5 的整段减量区（约 83–100 ms）。所以**不改代码**。
  - 已知差别：在这约 17 ms 里，R5 给 348–429（有时直接切），Reference 给 460，比 R5 宽容。
  - 如果以后要改回 R5 的做法，参考上表：剩余约 100 → 83 ms，出口从约 348 线性涨到 460。

**C-3 研究**：直接翻越（没有先攀爬，rise 44–75 u，42 次）的 R5 翻越时长 = 0.1743 + 0.00543·rise（rms 5.8 ms）。
- Unity 用的是 0.1728 + 0.0055·rise，两者相差不到 1 ms。
- 单次差 0 / 8 / 17 ms 是 R5 自己每次差 1–2 条命令的散布，不是公式错。
- 只有先攀爬再翻越、而且墙很高（h232，2–5 次）时，Unity 明显晚 25–42 ms。
- **结论**：不改。h232 等以后有更多数据再看。

**C-4 研究**：R5 走路接近的 15 次 superglide 里，402 的 3 次和 200 的 12 次在记录精度内分不出来：同一条命令接触，高度相同，x 差不到 1 u。
- 所以是命令内部碰墙的时刻决定的（大约 1 / 5 的概率）；以命令为单位的身体模拟不了。
- Reference 给的是多数结果（200）。
- **结论**：不改。

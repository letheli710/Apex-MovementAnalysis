# 枪的屏幕大小和曳光起点（R5）

会话 `recoil-view`，2026-11-03。回答 11-03 试玩的两个问题："枪在屏幕上比 R5 大"和"曳光像从眼睛射出"。第三个问题（换弹节奏）在同目录的 [RELOAD-MOTION.md](RELOAD-MOTION.md)。

**截图方法**：引擎 `screenshot` 命令，经 `ClientCommand` 发出，不占鼠标和焦点。工具在 `tools/`（`shots.py`、`fov_scale.py`、`tracer_single.py`）。全部原始帧放在 `HSD-RawData-GM`，这里只留有代表性的。

## 结论

| # | 结果 | 来源 |
|---|---|---|
| 1 | **枪在屏幕上的大小不随镜头 FOV 变**。`cl_fovScale` 1.0 / 1.27 / 1.5（镜头 70 / 89 / 105）下，枪的像素比例 1.005 / 1 / 1.000 | 实测 |
| 2 | 所以 **Unity 的枪要有一个固定的枪模 FOV**，不能跟镜头 FOV 走 | 由 1 推出 |
| 3 | 〔11-04 标注：65° 这个粗估已被 `IRON-SIGHTS` 取代，见 HSD-Unity #68 的枪模 FOV。下面的话留档。〕枪模 FOV 的绝对值粗估：**约 700 像素每单位正切**（1600×900），等于垂直 FOV 约 65°，水平约 98°。误差不小（640–750），要用截图校准 | 实测，粗估 |
| 4 | **S21 客户端的曳光从枪口出发，落到准星方向的落点** | 实测（画面） |
| 5 | **这只改画面，不改弹道**：客户端把"枪口点 − 子弹位置"加到子弹实体一个按时间衰减的显示偏移上 | 反编译 |
| 6 | 真实子弹（S3 dedi 判定）从眼睛出发，走的是准星方向。所以"子弹从眼睛出发"和"曳光从枪口出发"**都对**，一个是判定，一个是画面 | 实测（D 报告）+ 这次 |

**对 Unity 的建议**：判定不动，继续从眼睛走。只把画面上的曳光起点改到枪口，让偏移在飞行开始后很快衰减掉，末端对准判定落点。枪用单独的相机或固定 FOV 渲染。

## 2. 枪模 FOV

| 问题 | 结果 | 来源 |
|---|---|---|
| 是否乘 `cl_fovScale` | **不乘**。三个比例下枪几乎不变，见结论 1。图：[1.0](screens/fovscale_1.0.png)、[1.27](screens/fovscale_1.27.png)、[1.5](screens/fovscale_1.5.png) | 实测，R-301 |
| `viewmodelfov` 字段 | **没读到**。任务说是 70，但运行时的 1175 个武器字段里没有这个名字，`mp_weapon_rspn101.txt` 里也没有。只有 `zoom_fov_viewmodel`，腰射 0 | 字段 |
| 名字相近的设置 | `ss_viewmodelfov` = 54（名字看像分屏用，**没验证**）。`viewmodelfov`、`viewmodel_fov`、`cl_viewmodelfov` 都读回空 | 实测 |

**绝对值**：用枪口在镜头坐标下的位置和它在画面上的像素算比例（`像素 = 中心 + k × 右/前`）。R-301 的光束尾端在 (860, 527)，P2020 约 (885, 500)，得 k 约 640–750。这几个点是我看图取的，**精度有限，只能当起点**。各种猜法的 k：

| 假设 | k | 合不合 |
|---|---|---|
| 70° 按 4:3 再换 16:9 | 857 | 偏大 |
| 89° 水平 | 814 | 偏大，而且镜头变时枪不变，排除 |
| 89° 按 4:3 再换 16:9 | 610 | 偏小，同样排除 |
| 54° 垂直 | 883 | 偏大 |
| 实测 | 640–750 | |

**都不完全对得上，所以真实值没定**。Unity 这边最直接的做法：用同样的 16:9、同样的枪口坐标，调枪模相机 FOV，直到和这 8 张图重合。注意，**枪口位置是世界坐标**，不是屏幕位置。

## 3. 曳光起点

**画面**（`screens/tracer-key/`）。慢放（服务端 `host_timescale`）和正常速度都试了；慢放下多数帧已经过了，**有效的帧是正常速度**拍到的。

| 枪 | 状态 | 看到了什么 | 图 |
|---|---|---|---|
| R-301 | 站立 | 亮光束**从枪口连到准星旁的落点**。之后几帧光束淡去，留一条从落点指回枪口方向的淡尾 | [光束](screens/tracer-key/r301_stand_beam.png)、[之后](screens/tracer-key/r301_stand_after.png) |
| P2020 | 站立 | 同样，光束从枪口出发，三次都一样 | [光束](screens/tracer-key/p2020_stand_beam.png) |
| P2020 | 向右滑铲 | 光束在枪左上方，指向落点；落点在准星左边一点，因为人在向右移动 | [光束](screens/tracer-key/p2020_slide_beam.png) |
| Kraber | 站立 | 一条细光束从右侧进入落点，方向和枪口一致；爆光很强，**不如前两把清楚** | [光束](screens/tracer-key/kraber_stand_beam.png) |
| Kraber | 向右滑铲 | **看不清**：离墙太近，整屏爆光 | [爆光](screens/tracer-key/kraber_slide_washed.png) |
| R-301 | 向右滑铲 | 这几帧只拍到落点火花，**没拍到完整光束** | [图](screens/tracer-key/r301_slide.png) |

落点离枪近（靠近的墙），所以光束短；这些帧没有拍到打向远处时的样子。**枪口焰这几帧里都没看到**，可能只存在一两帧，这次没有确认。

**反编译**（`r5apex_dx12.exe`，Ghidra）：

| 地址 | 做什么 |
|---|---|
| `0x1406dd0e0` | 读武器设置：`+0x25` 是 `projectile_adjust_to_gun_barrel`（默认 1），`+0x26` 是 `projectile_adjust_to_hand`。两个都开时报错 |
| `0x1406c6850` | 子弹实体：两个里有一个开，且还没处理过，就把它加进客户端列表 |
| `0x14081efc0`（`cdll_client_int.cpp`） | 客户端每帧处理这张列表 |
| `0x1406c6c00` | 算差值：`目标点 − 子弹当前位置`。本地玩家第一人称时再乘一个系数（实体 `+0x1aa0`）。太远（超过一个上限）就不做。然后交给下一行 |
| `0x1406c69a0` | 取目标点：通常是武器的枪口点，`adjust_to_hand` 时是手 |
| `0x14076f560` | **把差值加到实体的显示偏移 `+0xd34`，并设结束时间 `+0xd30`**。这是一个随时间衰减的画面偏移 |

**结论**：这个字段**不改子弹的真实方向**，只改客户端的显示位置。这里读的是客户端；服务端（`r5apex_ds.exe`）里也有这个字段和一个"强制当作没开"的设置（`ForceAdjustToGunBarrelDisabled`），**服务端的用途我没有反编译**。

**推断**（没单独验证）：

- 系数 `+0x1aa0` 很可能是字段 `projectile_first_person_offset_fraction`，这些枪都是 0.5。如果是这样，光束起点在眼睛和枪口的正中间。方向和枪口一致，所以画面上仍然压在枪口上。
- 衰减时间有上限：`min(设置值, 距离设置 / 子弹速度)`。`projectile_muzzle_offset_decay_max_time` 这些枪都是 0，表示用全局设置。全局设置的名字和值**没读到**。

**S21 显示和 dedi 判定各是什么**：

| | 是什么 | 来源 |
|---|---|---|
| S21 客户端的曳光 | 从枪口开始，偏移很快衰减，末端落到真实弹道上 | 实测（画面）+ 反编译 |
| S3 dedi 的判定 | 从眼睛出发，方向是瞄准方向（第一发水平偏差 0.00 u） | 实测（D 报告） |
| S21 正式服务器的判定 | **这里测不到** | |

# B5：R-301 开镜回落慢 0.04 s，读代码的结果

2026-11-13，会话 `r5gap-code`。补测单 `R5-GAP-TESTS-1113.md` 的 B5，**只读代码，没有进游戏**。

## 先说结论

**代码读完，没有找到能解释这 0.04 s 的规则差别。** R5 的回落弹簧、k 和 d 的混合、热度的消退，都和 Unity 用的公式一致。读代码排除了几个原因，也找到两个只有进游戏才能确认的候选，以及一处文档和脚本对不上的地方。

问题本身（RECOIL-VIEW §10.3）：R-301 开镜连射 21 发，停火后 punch 降到峰值一半，R5 用 0.244 s，Unity 规则模拟带随机平均 0.203 s、不带随机 0.175 s。服务端纠正那一跳已经排除。

## 读到的规则 [反编译]

```
每条用户命令（玩家移动处理 0x140a54e80 里）调用 0x140a34170：
  1. 镜头自己的 punch（玩家 +0x2430 / +0x243c）走一步
  2. 武器 punch 先加上移动数据里的一个修正量（movedata +0x18..+0x20）
  3. 武器 punch（+0x2448 角度 / +0x2454 速度）走一步
  4. 枪模 jolt（+0x3514 / +0x3520）走一步，用 viewmodel_spring_jolt
走一步：
  k、d = lerp(冷弹簧, 热弹簧, 热度)，再 lerp(腰射, 开镜, zf)       0x140712920
  热度 = clamp(停火时热度 − (时间 − 开始消退时间) / fadetime, 0, 1)  0x140713060
  三轴各自用解析解（过阻尼 / 临界 / 欠阻尼三种）                    0x140521af0
  |x|² + |v|² ≤ 0.001 时归零                                       0x140a33ee0
```

字段偏移（武器 `+0x19d0` 起）：`viewkick_spring` 0x718、`_hot` 0x71c、`_heatpershot` 0x720、`_cooldown_holdtime` 0x724、`_cooldown_fadetime` 0x728、`viewmodel_spring_jolt` 0x72c。

## 排除了什么

| 候选 | 结论 | 依据 |
|---|---|---|
| 热度不是线性消退 | 排除：线性，斜率 −1 / fadetime | `0x140713060` |
| k、d 不是线性混合 | 排除：先按热度、再按 zf，都是线性 | `0x140712920` |
| 弹簧每帧的解法不同 | 排除：解析解，按这一步的时长；RECOIL-VIEW 用记录的 x、v、k、d 逐帧重算，误差 0.00003° | `0x140521af0` |
| 归零阈值提前把 punch 清掉 | 排除：只在 √0.001 ≈ 0.03° 以下，远小于半峰 | `0x140a33ee0` |

## 还没排除的（要进游戏）

1. **另一条积分路径。** `0x140a34170` 每一步先问一个虚函数（`DAT_1434519a8` 的 `+0xb50`），返回假时不用解析解，改用 `0x140a7b850`：固定步长 0.0166 s 的显式积分，速度乘 `exp(−d·0.0166)`，角度夹在一个范围里。客户端记录和解析解吻合，说明客户端走的是解析解；**S3 dedi 走哪条不知道**。如果 dedi 走另一条，服务端的 punch 会和客户端慢慢分开，纠正就不只是那一次 −0.85° 的跳变。用 `b5sim.py` 粗算（同一 k、d 时间表，60 Hz 步长），另一条解法的半峰时间比解析解**短** 0.02–0.03 s，方向和 R5 相反，所以就算 dedi 走它，也**解释不了** R5 更慢。
2. **热度用的时钟。** `0x140713060` 平时用当前时间（`globals +0x28`），但武器满足一组条件时改用武器 `+0x1570` 的时间。如果停火后走的是后者，而它落后当前时间，热度消退就整体推迟。RECOIL-VIEW 记的热度从 0.084 s 开始降，和字段 0.08 只差一帧，看起来没推迟；但那次读的是不是这个函数的返回值没有写明。
3. **修正量。** 每步加到 punch 上的 movedata `+0x18..+0x20` 是什么没读（RECOIL-VIEW §7 推断它和鼠标抵消有关）。不动鼠标时应该是 0，没验证。

## 文档和脚本对不上的一处

RECOIL-VIEW §2.2 表头说"时间从回落峰值算起"，但算这张表的 `recoil-view/analyze.py`（`return_metrics`）是**从最后一发算起**（`r["t"] - tl`）。0.244 s 是从最后一发算的。Unity 那边的 0.203 / 0.175 s 是不是同样从最后一发算，要查 `TheAmplitudeMatchesRecoilView` 那一侧的代码。**如果两边起点不同**（一个从最后一发，一个从峰值，R5 峰值在最后一发后 0.067 s），差出来的就有一大半是口径，不是规则。这是最便宜、最先该查的一步。

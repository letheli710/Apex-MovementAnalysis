依据：

## 1. 大白话

现在的走路不是动画片段，而是程序算出来的：
- 骨盆按一张「关键姿势表」起伏和摆动；
- 两只脚用 IK 踩在地上，脚掌绕脚尖或脚跟滚；
- 腿的长度写死在 `TitanSkeleton` 里，用的是中型 v2 的数。

所以给重型「重定向」，主要不是改动画，而是三件事：
1. 把腿长等尺寸从写死的常数改成按底盘取；
2. 给重型写一张自己的关键姿势表（步长、两脚距离、骨盆起落）；
3. 用录像工具量脚滑、脚离地、脚插地，调到合格。

**最大的风险就是 B-沉 现在的滑步问题。** 在中型上，滑步来自踝角碰到 −35° 的上限。我算了一下：重型小腿短、膝盖低，骨盆降同样多的时候，踝要多弯 3–8°，会更早碰到上限。B-沉 那个「踝放到 −45°」的开关，在重型模型上也用不了：Blender 里实测，踝弯过 −35° 到 −40° 之间时，脚趾就顶进小腿了。所以重型的办法是**骨盆少降一点**，「沉」的感觉靠上身和手臂来做（TF2 也是这么做的，F1、F5）。

## 2. 现在的 B-沉 是怎么做出来的

| 部分 | 做法 | 位置 |
|---|---|---|
| 步伐时钟 | 按走过的距离推进，不按时间。一个周期 = 两步；周期 = clamp(速度 × 基础周期, 最短 2.4 m, 步长 × 2) ÷ 速度。起步低于约 1.7 m/s 时按时间 | `TitanBodyCore` 约第 580 行 |
| 姿势 | `TitanWalkKeyPoses.WalkHeavy`：左半周期 4 行（contact 0.00 / down 0.08 / passing 0.23 / high 0.37），右半周期自动镜像。每行：骨盆前、侧、高，俯仰、滚转、扭转，腰弯、侧弯、扭转，爪臂摆动，到下一行的缓动（Drop / Smooth / Fall） | `TitanWalkKeyPoses.cs` |
| B-沉 的数 | 步长 105 u = 2.67 m（B 是 138.3 u），每只脚离中线 0.90 m。骨盆高 −0.26 / −0.34 / −0.16 / −0.12 m，比 B 低约 0.10 m。摆动比 B 小（滚转 3.6°、扭转 7°） | 同上 |
| 腿 | 两骨 IK（`TitanSkeleton.SolveLeg`）：大腿 1.40、小腿 0.75、踝高 0.70、髋 y ±0.86。数据来自 v2 `design.py`，都是 `const` | `TitanSkeleton.cs` 第 22–27 行 |
| 脚 | 踩住时接触点（脚尖 1.13 m 或脚跟 −0.57 m）在世界里不动，脚掌绕它滚；抬起时走弧线 | `TitanFeet.cs` |
| 骨盆高度修正 | 踩住的腿超过 0.98 × 腿长时先降骨盆；超过 `heelReach` 0.98 时把脚跟顶起，每次 1°（`heelStep`） | `TitanBodyCore` 1150–1210、1297–1311 |
| 踝角保护 | 每只脚在给定的滚转上再加一点，让踝留在 −35…60° 以内（第 1281 行） | 同上 |
| 开关 | `walk_style`（默认 `b_heavy`）、`b_heavy_ankle`（默认 −35） | `TitanConfig` |

**−35° 滑步的来历**（README 第三轮，`feet.tsv`）：

- B-沉 在 100 m 里滑 4.93 m。其中 97 % 出在支撑的后 40 %（脚跟已经抬起，只有脚尖着地），93 % 出在踝角卡在 −35° 的那些帧。
- 原因：B-沉 骨盆低，支撑后段膝盖更弯、小腿更往前倾，踝要往上弯过 35° 才能让脚保持给定的滚转。卡住之后，骨架把脚掌多转了 4–6°，脚尖（离踝 1.13 m）就离开了原来站的点。
- B 碰不到这个上限（最差约 −31°），只滑 2.03 m / 100 m。
- 试过的办法里，只有把踝上限放到 −45° 有效（0.41 m / 100 m）。但这超出了模型设计的范围，所以做成开关，默认关。

| 髋 z（直腿） | 2.85 | 2.50 | |
| 髋 y | ±0.86 | ±1.055 | 髋间距 2.11 |

| 腿全长 `LegMax` | 2.15 | 2.107 | 只短 2 % |
| 踝高 | 0.70 | 0.39 | |

| 0.98 腿长时的膝角 | 24.1° | 25.6° | |
| 肩 y / z、上臂、前臂 | 1.30 / 4.55、0.90、0.85 | 1.76 / 4.78、0.95、0.95 | 第一人称手臂、炮口要跟着改 |
| 炮长（肘到炮口） | 2.00 | H-1 1.40；H-2 3.40 | |
| 站姿骨盆 `StandPelvisZ` | −0.14 | 先按 −0.06 起（重型 `stand_aim` 量出骨盆 3.013 − 3.07），再在录像里对 | |
| 走速 / 冲刺速度 | 250 / 380 | **210 / 310**（`TitanChassis.Heavy()` 已有） | 动画里有几处把 250 写死了（`TitanBodyCore` 第 564、715 行），要改成读底盘 |
| 踝上限 | −35（开关可到 −45） | **只能 −35**（Blender 实测：踝弯到 −40° 时，脚趾件和小腿有 42 处相交，−45° 时 54 处） | 想放宽，要先改模型：把小腿前下角削掉，或者把脚趾顶面压低 |

**步长和步频**：

TF2 的三种底盘走路用同一套片段：一个周期 1.133 s、一步 0.57 s、步幅 139.5 u（F1）。重型的「重」不靠步子短。重型骨架已经统一乘了 0.878（H-SK8），所以 TF2 的步幅换到重型就是 139.5 × 0.878 = 122.5 u = 3.11 m。

| 方案 | 一步 | 走速 210 u/s 时一步 / 一周期 | 对照 | 推荐 |
|---|---|---|---|---|
| **G1 TF2 步幅 × 0.878** | 122.5 u = 3.11 m | 0.583 s / 1.17 s | TF2 一步 0.57 s，F1 建议 0.55–0.6 s；第一人称镜头定时器 0.70 s，差 0.12 s（中型 B-沉 差 0.28 s） | **默认** |
| G2 B-沉 步幅按腿长换算 | 105 × 2.107 / 2.15 = 103 u = 2.62 m | 0.49 s / 0.98 s | 保留 B-沉「步子碎」的样子 | 开关，和 G1 一起录给用户比 |
| G3 照 B 的 138.3 u | 3.51 m | 0.66 s | 支撑的距离更长，后段踝更吃紧 | 不做 |

- **两脚宽**：每只脚离中线 1.10 m（= 髋 y 1.055 + 0.045，和 B-沉 在中型上 0.90 − 0.86 的关系一样）。两脚内侧间隙 0.98 m（鞋底半宽 0.61）。另录 1.20 做比较。TF2 重型待机时两脚中心距 124 u = 3.15 m（±1.57），那是待机站姿；走路时的脚宽 TF2 没有量过。
- **骨盆起落（姿势表的 `pelZ`）**：从 B 的表出发，**整体抬高约 0.06 m**，作为起点：contact −0.14、down −0.19、passing −0.02、high 0.00。理由：几何估算，骨盆降得一样多时，重型的踝要比中型多弯 3–8°；B 在中型上最差 −31°，抬 0.06 m 后，重型应该回到约 −31°。最后以录像里 `feet.tsv` 的踝角为准。
- **「沉」放在哪**：重型的腿占身高 42 %，本来就显得矮。B-沉 的「沉」不再用骨盆下沉来表现，改成：
  - 爪臂摆动减半（F5：TF2 重型冲刺时空手的肩只摆 1.9°）；
  - 骨盆滚转、扭转用 B-沉 的小值（3.6° / 7°）；
  - 第一人称每步的竖直冲量用重型的 −4 u/s（F12，`TitanCamParams.For(chassis)` 已经有了）。
- **跑、冲刺跑**：表的结构不变，步长按 0.878 换算（跑 161 → 141 u；冲刺跑按 310 u/s × 0.87 s ÷ 2 = 135 u）。这一轮只量脚滑、不调姿势；如果超过中型的值，记成遗留问题。

## 4. 改在哪里（不和轻型碰同一批文件）

轻型会话之后也要做一样的事。会冲突的只有「把写死的中型尺寸改成按底盘取」这一步：它要动 `TitanSkeleton.cs`、`TitanBodyCore.cs`、`TitanFeet.cs`、`TitanClips.cs`、`TitanBodyAnimator.cs`、`TitanWalkFilm.cs` 和测试。所以分成三段：

| 段 | 内容 | 分支 / 工作树 | 动哪些文件 |
|---|---|---|---|
| **C0 共用（只做一次，轻型、重型都等它）** | 把 `TitanSkeleton` 的常数换成一个按底盘取的尺寸对象（`TitanDims.Medium` = 现在这套数）。`TitanBodyCore` 的步态表改成从尺寸对象取（`dims.walkGait`、`dims.runGait`…）。两处写死的 250 改读 `chassis.walkSpeed`。`TitanWalkFilm` 加 `-chassis light/medium/heavy`，并加写 `joints.tsv`（每帧全部关节角，给第 5 节的 Blender 复核用）。**验收：中型的走、走跑冲刺两条路线，`body/steps/slide/feet.tsv` 和改前逐字节相同** | 从 `titan/walk-compare` 510c971 开 `titan/dims`，工作树 `HSD-Unity-TITAN-DIMS` | 上面列的共用文件 |
| **H 重型（本方案）** | 新文件 `TitanDimsHeavy.cs`（第 3 节的数）、`TitanWalkKeyPosesHeavy.cs`（G1 表 + G2 表）、`TitanAnimHeavyTests.cs`；重型模型的 prefab（导入 `Titan_H1.fbx`，节点名和 v2 相同） | 从 `titan/dims` 开 `titan/walk-heavy`，工作树 `HSD-Unity-TITAN-HWALK`（新建在 C 盘） | **只加新文件**；共用文件里一行也不改。需要钩子就回到 C0 加 |
| L 轻型 | 同样只加自己的新文件 | `titan/walk-light`，自己的工作树 | 和 H 没有共同文件 |

谁做 C0 由 lead 定。我建议本会话做，C0 合并以后轻型、重型再并行。

还有一处和动画有关、但不属于走路的：上下机、跪姿、死亡片段读的是 `TitanPoseData`（v2 的 19 个姿势）。换成重型尺寸以后，这些片段的脚位要用重型自己的数据：可以从本文件夹导出一份 `heavy_spec.json`，用同一个生成脚本生成 `TitanPoseDataHeavy.gen.cs`，也是新文件。这一步算 H 段里的一个小项（第 6 节 H5）。重型默认跪姿的数据就在这里（R5 的 H-P3）。

## 5. 怎么验证：脚不离地、不插地、不滑

都用 `TitanWalkFilm`（真的 `TitanSim` + 真的模型、空平地、60 Hz），加 `-chassis heavy`。路线：
- 走：静止 1 s → 走 6 s → 停 2.5 s；
- 走跑冲刺：现有路线；
- 原地转身：45°/s 4 s，再 180°/s 1 s。

| 检查 | 怎么量 | 合格线 |
|---|---|---|
| 不滑 | 现有的 `slide.tsv`：踩住的脚，接触点（脚尖或脚跟）的水平移动累计，从关节角算 | 走 ≤ 2.0 m / 100 m（中型 B 的水平）；硬上限 4.93（中型 B-沉 现在的值）。冲刺 ≤ 1.5；转身 ≤ 0.72 m（中型的值） |
| 踝不碰上限 | `feet.tsv` 的踝角 | 走路时卡在 −35° 的帧 = 0；最差 ≥ −33°（留 2° 余量） |
| 不离地 | 踩住的脚的接触点高度（`steps.tsv`），以及现有的「落地脚够不着地 最大 m」 | 接触点 \|z\| ≤ 1 cm；够不着 = 0 |
| 不插地 | 新加：按 `joints.tsv` 在 Blender 里用真实重型网格（`build_heavy.py` 的部件）每 5 帧摆一次姿势，量 `Foot_*`、`Toe_*`、`Shin_*` 的最低点 | 踩住时最低点在 −2 cm 到 +1 cm 之间（倒角是 3 cm）；抬起的脚离地 ≥ 5 cm（经过另一只脚时 ≥ 10 cm） |
| 不穿模 | 同一次 Blender 复核：本文件夹已有的 BVH 部件碰撞（排除表和 R5 相同） | 走、跑、冲刺、转身全程 0 帧穿模；有的话列出来（第一版允许 ≤ 1 % 帧，写明哪一对） |
| 模拟不受影响 | `NoWalkStyleChangesTheSim`、`TheAnimatorChangesNothingInTheSim` | 通过 |
| 中型不受影响 | C0 的逐字节对照；H 段只加新文件 | 逐字节相同 |
| 节奏 | `steps.tsv` 的一步时长 | G1 在 210 u/s 时 0.55–0.62 s |
| 看 | 侧面、正后方、斜后方 30 fps 录像，G1 / G2 / 两种脚宽并排；关键姿势截图 | 给用户选 |

单次录像约 3 分钟（README），Blender 复核一次走路路线（每 5 帧，约 110 帧）约 5 分钟。

## 7. 要 lead 定的事

1. 默认步幅：G1（TF2 × 0.878，3.11 m，一步 0.58 s，推荐）还是 G2（B-沉 换算，2.62 m，0.49 s）。我的打算是两个都做、都录，默认先放 G1，最后由用户选。
2. C0 谁做：建议本会话做，轻型等它合并。
3. 踝上限：重型只能用 −35°。如果用户想要 B-沉 那样低的骨盆，就要改模型（削小腿前下角），那是 v3/H 的模型工作，不在这份方案里。
4. 重型 prefab 的导入，是放在本方案里（H4），还是交给专门做 Unity 导入的会话。
